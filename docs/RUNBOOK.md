# Runbook

Operational manual for running, configuring, and troubleshooting this
project. For what the code does architecturally, see
[ARCHITECTURE.md](ARCHITECTURE.md).

## Prerequisites

- Python 3.12+ and [`uv`](https://docs.astral.sh/uv/)
- A Google Cloud project with the **Vertex AI API** (`aiplatform.googleapis.com`) enabled
- Google Cloud CLI (`gcloud`), authenticated
- A Roboflow account with an API key that's authorized for **serverless** inference (see [Roboflow](#roboflow) below — this tripped us up during setup)

## Credentials

Two separate credential systems are in play; neither secret lives in this repo.

| Credential | Where it lives | How it's loaded |
|---|---|---|
| Google Vertex AI | `~/keys/google-key.json` (Application Default Credentials, generated by `gcloud`, **not** a downloaded service-account key) | `GOOGLE_APPLICATION_CREDENTIALS` environment variable, set in your shell or PyCharm run config |
| Roboflow | `.env` in the project root (`ROBOFLOW_API_KEY=...`) locally, or `--set-env-vars`/Secret Manager on Cloud Run | `load_dotenv()`, called at import time in both `main.py` and `app.py` |

`.env` is listed in `.gitignore` — confirm with `git check-ignore -v .env` before ever running `git add .` in this repo.

### Setting up Google credentials from scratch

```bash
brew install --cask gcloud-cli   # if not already installed
gcloud auth login
gcloud config set project cloudrun-hack26nyc-4392
gcloud services enable aiplatform.googleapis.com
gcloud auth application-default login
mkdir -p ~/keys
cp ~/.config/gcloud/application_default_credentials.json ~/keys/google-key.json
chmod 600 ~/keys/google-key.json
```

**Why ADC and not a service-account JSON key?** The original plan was a
downloaded service-account key (the classic approach). On this project,
granting the service account a role via `gcloud projects add-iam-policy-binding`
was rejected — `Policy update access denied` — even though the logged-in
account showed `roles/owner`. That's consistent with an IAM deny-policy
on a shared/sandboxed GCP project (this one came from a hackathon), which
is common in temporary lab environments to stop participants from
escalating privileges. Application Default Credentials sidestep the
problem entirely by reusing your own account's existing permissions
instead of creating a new principal — and it's Google's current
recommendation for local dev anyway.

### Setting up the Roboflow key

1. Get your key from the Roboflow dashboard: **Settings → Roboflow API Keys**.
2. Put it in `.env`:
   ```
   ROBOFLOW_API_KEY=your_key_here
   ```
3. Verify it works *before* trusting it — Roboflow returns different error
   messages depending on which endpoint you hit, and they don't all mean
   the same thing (see [Troubleshooting](#troubleshooting)):
   ```bash
   uv run python3 -c "
   from inference_sdk import InferenceHTTPClient
   import numpy as np
   client = InferenceHTTPClient(api_url='https://serverless.roboflow.com', api_key='YOUR_KEY')
   print(client.infer(np.zeros((100,100,3), dtype='uint8'), model_id='vehicle-detection-3mmwj/1'))
   "
   ```
   A successful call returns a dict with an empty `predictions` list (there's nothing to detect in a blank black image) — that's still success.

## Running it

```bash
uv sync                # first time only, installs from uv.lock
export GOOGLE_APPLICATION_CREDENTIALS=~/keys/google-key.json
uv run main.py
```

What happens:
1. Fetches all ~968 cameras from the NYC DOT API, filters to online ones (~960+).
2. Opens a browser tab with a live camera image (left pane) and a map of every camera (right pane), the current one highlighted in red.
3. Every 10 seconds, both the terminal and the browser tab advance to the next camera in the same order (see the synchronization note in [ARCHITECTURE.md](ARCHITECTURE.md#important-design-note-two-independent-rotation-loops) — they're not perfectly locked together).
4. Terminal prints, per camera: a one-sentence Gemini description and a Roboflow vehicle count.
5. `Ctrl+C` stops the loop.

### PyCharm

- **Python interpreter**: this project's own venv — `.../nyc-dot-cams/.venv/bin/python`
- **Script path**: `.../nyc-dot-cams/main.py`
- **Environment variables**: `GOOGLE_APPLICATION_CREDENTIALS=/Users/wilmccann/keys/google-key.json`
- **Paths to .env files**: leave empty — `main.py` loads `.env` itself via `python-dotenv`

### Running `app.py` (the Cloud Run service) locally

Same credentials as above, different entry point:

```bash
export GOOGLE_APPLICATION_CREDENTIALS=~/keys/google-key.json
uv run uvicorn app:app --port 8080
```

Open `http://localhost:8080/`. Unlike `main.py`, nothing opens a browser
for you — this is a normal web server, so you navigate to it yourself.
Watch the terminal for structured log lines as `rotation_loop()` completes
each cycle; poll `curl http://localhost:8080/api/status` to see the raw
JSON a viewer's page is fetching.

## Google Cloud Run

**This app has been deployed to Cloud Run and verified working** — `app.py`,
per the design in
[design/cloud-run-deployment.md](design/cloud-run-deployment.md). `main.py`
still never runs there; only the FastAPI service does.

What Cloud Run actually is, briefly: a serverless container platform. You
give it a container image (here, built automatically from the `Dockerfile`
via Cloud Build — no manual `docker build` needed, and useful because
Docker isn't even installed in this dev environment); Cloud Run runs it,
scaling instances up and down — including to zero — based on traffic.
Billing is per-request/per-100ms-of-CPU-and-memory while handling traffic
(or a fixed cost for pinned `min-instances`, which this deployment uses —
see below), not a flat monthly server price.

### Deploying: `scripts/cloud-run-start.sh`

```bash
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com \
  --project=cloudrun-hack26nyc-4392   # one-time, if not already enabled

./scripts/cloud-run-start.sh
```

The script reads `ROBOFLOW_API_KEY` out of `.env` (erroring clearly if
it's missing) and runs:
```bash
gcloud run deploy nyc-dot-cams \
  --source . \
  --region us-central1 \
  --project cloudrun-hack26nyc-4392 \
  --no-allow-unauthenticated \
  --min-instances=1 \
  --max-instances=1 \
  --memory 1Gi \
  --set-env-vars ROBOFLOW_API_KEY=...
```
then prints the deployed URL and the proxy command to view it. This is
the exact command used for the original verification deploy — the script
just wraps it so the key never needs pasting into a terminal by hand.

`--source .` hands the whole repo to Cloud Build, which builds the
`Dockerfile` and deploys the result — this is what got build-tested
(successfully) even though a plain local `docker build` never was.
`--no-allow-unauthenticated` keeps it private by default (see
[making it public](#making-it-publicly-reachable) below for the flag that
opens it up). No `GOOGLE_APPLICATION_CREDENTIALS` is set here on
purpose — see [Credentials on Cloud Run](#credentials-on-cloud-run) below.

### A real IAM error hit during the first deploy attempt

The first attempt failed at the "uploading sources" step:

```
PERMISSION_DENIED: Build failed because the default service account is
missing required IAM permissions. ... IAM permission denied for service
account 696207924611-compute@developer.gserviceaccount.com.
```

Cloud Build (triggered by `--source .`) runs as the project's default
Compute Engine service account, which didn't have read access to the GCS
bucket Cloud Build auto-creates to stage uploaded source
(`run-sources-<project>-<region>`). The obvious fix —
`gcloud projects add-iam-policy-binding ... --role=roles/storage.objectViewer`
— hit the **exact same** `Policy update access denied` deny-policy
documented in [Credentials](#credentials) above; this sandbox project
blocks project-level IAM changes categorically, not just for custom
service accounts.

**What worked:** granting the same role at the *bucket* level instead of
the *project* level:
```bash
gcloud storage buckets add-iam-policy-binding gs://run-sources-cloudrun-hack26nyc-4392-us-central1 \
  --member="serviceAccount:696207924611-compute@developer.gserviceaccount.com" \
  --role="roles/storage.objectViewer"
```
This succeeded where the project-level grant didn't — the deny-policy
appears scoped to `resourcemanager.projects.setIamPolicy` specifically,
not to IAM changes on individual resources (buckets, and later services —
see below). **General lesson for this sandbox:** if a project-level IAM
grant is denied, try the same grant scoped to the specific resource
before concluding it's impossible.

After that one-time bucket grant, the deploy above succeeded outright —
including the actual Vertex AI and Roboflow calls working immediately at
runtime, with no further IAM changes needed for the runtime service
account (see next section).

### Credentials on Cloud Run

No JSON key file, no `GOOGLE_APPLICATION_CREDENTIALS` — the deployed
service runs as the project's default Compute Engine service account
(`696207924611-compute@developer.gserviceaccount.com`, confirmed via
`gcloud run services describe nyc-dot-cams --format="value(spec.template.spec.serviceAccountName)"`),
which Vertex AI calls authenticate against automatically. This account
already had sufficient Vertex AI access with no explicit grant needed —
worth re-checking if this is ever deployed under a different, less
permissive GCP project. `ROBOFLOW_API_KEY` was passed via
`--set-env-vars` for this verification deploy, which is simpler but
weaker than the Secret Manager approach the design doc recommends for a
real production deployment — fine for a one-off verification, not for
something staying up long-term with secrets visible in the service's
revision config.

### Verifying it after deploy

Since it's deployed authenticated-only by default, a plain browser tab
can't load it (no way to attach an auth header via navigation). Two ways
to check it:

**Authenticated proxy** (keeps it private):
```bash
gcloud run services proxy nyc-dot-cams --region us-central1 --project cloudrun-hack26nyc-4392 --port 8081
```
Then open `http://127.0.0.1:8081/` normally — the proxy attaches your
`gcloud` identity token for you.

**Direct curl with an identity token:**
```bash
TOKEN=$(gcloud auth print-identity-token)
curl -H "Authorization: Bearer $TOKEN" https://nyc-dot-cams-696207924611.us-central1.run.app/api/status
```

### Making it publicly reachable

To let a plain browser hit the URL directly with no token:
```bash
gcloud run services add-iam-policy-binding nyc-dot-cams \
  --region us-central1 --project cloudrun-hack26nyc-4392 \
  --member="allUsers" --role="roles/run.invoker"
```
This is a **service-level** IAM binding, same category as the bucket-level
grant above — it worked despite project-level bindings being blocked. No
credentials are exposed by doing this (they only ever live server-side);
it just means anyone with the URL can load the page and generate traffic
against the one pinned instance.

### Tearing it down: `scripts/cloud-run-stop.sh`

This deployment bills continuously while it exists (`min-instances=1`
means an always-on instance, and the rotation loop makes real paid
Vertex AI/Roboflow calls every 10 seconds the whole time — see
[PRODUCTION_READINESS.md](PRODUCTION_READINESS.md#cost-the-thinking-token-problem)).
Don't leave a verification deploy running unattended:
```bash
./scripts/cloud-run-stop.sh
```
Runs `gcloud run services delete nyc-dot-cams --region us-central1 --project cloudrun-hack26nyc-4392`.
Redeploying later is just `./scripts/cloud-run-start.sh` again — nothing
about the teardown is destructive to the code or config, only to the live
running instance.

## Roboflow

Roboflow is a computer-vision platform: dataset labeling, model training,
and model hosting. This project only touches the hosting/inference side.

Two ways to run a Roboflow model, and this project's history with both:

- **Hosted (serverless) inference** — `https://serverless.roboflow.com`,
  called via `inference_sdk.InferenceHTTPClient`. No local compute, no
  Docker. **This is what `main.py` uses.** Requires an API key
  specifically authorized for serverless calls — the first key we tried
  authenticated fine everywhere else but was explicitly rejected here
  (`401: This key is not authorized for serverless inference`), which
  points at a plan/tier restriction, not a typo.
- **Local inference** — `inference server start` runs a Docker container
  on your own machine and you call `http://localhost:9001`. Free-tier
  keys that can't do serverless calls typically *can* do this. We didn't
  go this route only because Docker wasn't already installed and the
  deadline was tight; see [`docs/roboflow-local-inference.md`](#recommended-follow-up-docs) idea below if this changes.

**The model in use**, `vehicle-detection-3mmwj/1`, is a **public Roboflow
Universe model** — not something in this project's own workspace. The
workspace tied to the working API key (`star-developer-4392`, "Will Stars
Workspace") has zero trained projects of its own. Roboflow lets any valid
key call any *public* model by its `project-slug/version` ID, which is
what makes this work despite the empty workspace.

**Relevant docs:** [Roboflow Inference SDK](https://docs.roboflow.com/inference/http-inference) · [Run a model locally](https://docs.roboflow.com/guides/run-a-model-locally) · [Serverless API](https://docs.roboflow.com/deployment/roboflow-cloud/serverless-api) · [Roboflow Universe](https://universe.roboflow.com/) (where `vehicle-detection-3mmwj` lives)

## Troubleshooting

Real issues hit while building this, in case they recur:

**`Illegal name of environment variable: '<garbage bytes>'` in PyCharm**
The "Paths to .env files" field (separate from "Environment variables")
was pointed at a binary file and PyCharm tried to parse it as `KEY=VALUE`
text. In our case it had the venv's `python` binary path in it. Clear
that field — `main.py` loads `.env` itself, PyCharm doesn't need to.

**`SyntaxError: unknown parsing error` pointing at `.venv/bin/python`**
The **Script path** field had the interpreter binary in it instead of
`main.py`, and separately the **Python interpreter** dropdown was
pointed at a *different project's* venv. Both fields need to be set
correctly and independently — script path is "what file to run," Python
interpreter is "which venv's `python` runs it."

**`gcloud.projects.add-iam-policy-binding: ... Policy update access denied`**
Despite the account showing `roles/owner`. Seen on a hackathon-provisioned
GCP project — treat it as an IAM deny-policy on the sandbox, not a bug in
your command. Workaround: use Application Default Credentials (your own
account's permissions) instead of creating and granting a new service
account.

**Roboflow `401` errors that don't mean the same thing**
- `"This API key does not exist (or has been revoked)"` from the classic
  `roboflow` package's `check_key()` — the key itself is bad (typo, stale
  copy, actually revoked). Get a fresh one from the dashboard.
- `"Unauthorized api_key. This key is not authorized for serverless
  inference"` from `inference_sdk` — the key is valid and recognized, but
  this specific action (hosted/serverless calls) isn't permitted for it.
  Different problem, different fix (see [Roboflow](#roboflow) above).

**`inference_sdk` error: `Unknown type of input (bytes) submitted`**
Despite docs suggesting raw bytes work, `InferenceHTTPClient.infer()`
wants a decoded image (numpy array / PIL image), not a raw JPEG byte
string. Decode first: `cv2.imdecode(np.frombuffer(frame, dtype=np.uint8), cv2.IMREAD_COLOR)`.

**Vertex AI `UserWarning: This feature is deprecated`** *(resolved)*
`vertexai.generative_models` was being retired **June 24, 2026** in favor
of the `google-genai` SDK — `pipeline.py` migrated onto `google-genai`
(see [CODE_WALKTHROUGH.md](CODE_WALKTHROUGH.md#build_vertex_client--build_roboflow_client)),
so this warning no longer appears. Left here in case an older branch or
a reverted change brings it back — see the
[migration guide](https://cloud.google.com/vertex-ai/generative-ai/docs/deprecations/genai-vertexai-sdk)
if so.

**Cloud Run source deploy fails: `PERMISSION_DENIED ... missing required IAM permissions`**
Cloud Build's default service account lacks read access to its own
auto-created source-staging bucket, and the obvious project-level IAM fix
is blocked by the same deny-policy documented above. Fix: grant the role
at the **bucket** level instead of the project level — see
[A real IAM error hit during the first deploy attempt](#a-real-iam-error-hit-during-the-first-deploy-attempt).
The general pattern (resource-level IAM grants work even when
project-level ones are denied) also applies to making the Cloud Run
service itself public — see
[Making it publicly reachable](#making-it-publicly-reachable).

**`gh` push fails with `could not read Username for 'https://github.com'`**
The system had an ancient `gh` CLI (v2.0.0, from 2021) at `/usr/local/bin/gh`
that predates the `gh auth setup-git` subcommand used to wire `gh`'s stored
token into git's credential flow. A newer `gh` (installed via
`brew install gh`) landed at `/opt/homebrew/bin/gh` instead of replacing
the old symlink. If `gh --version` reports `2.0.0` in a fresh terminal,
that's the stale one — either fix `PATH` ordering or remove the old
`/usr/local/bin/gh` symlink.
